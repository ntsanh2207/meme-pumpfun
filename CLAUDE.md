# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A pump.fun "graduated memecoin" system: it collects tokens that graduated from the bonding curve to PumpSwap, backtests a "buy N minutes after graduation" strategy, paper-trades the strategies live, and can turn live signals into real swaps. Plain Python 3 scripts (stdlib + `numpy`; `solders` only for live trading) plus a single-page web app. There is no build step, test suite, linter config, or dependency manifest.

## Running locally

Every script lives flat in `app/` and imports its siblings by module name (`import analyze as A`, `import rules`, `import collector as C`, `import notify`), so run them as `python3 app/<script>.py` from the repo root. Most default to `data/` relative to the cwd; `server.py` defaults to `app/data`, so pass `--data data`.

```sh
deploy/pull_db.sh                                   # snapshot the VPS databases + reports into data/
python3 app/analyze.py --db data/pump.db --out data/report.json   # full backtest + rule search
python3 app/analyze.py --rules-only                 # backtest only the saved rules (settings/rules.json)
python3 app/analyze.py --history-only               # rebuild history.json from saved runs
python3 app/server.py --port 8090 --data data       # web app
python3 app/collector.py --days 7 --out data        # fetch graduates + 1m candles (slow, hits public APIs)
python3 app/watch.py --data data                    # live paper trading (runs forever)
python3 app/trader.py --data data                   # signal -> swap executor (runs forever)
```

The web app requires a login: `data/settings/login.json` holds `{"salt", "hash"}` (PBKDF2-SHA256), checked in `server.py:password_ok`. A view-only guest password lives in `data/settings/guest.json` (same format): a guest session (`role` "guest", tied to that file's hash, so replacing it signs guests out) may only GET `GUEST_GET` and `/api/strategy/*` (the Lab and Trading pages) and use the Coins Review and Wallets Review pages in full (`radar.GUEST_GET` / `radar.GUEST_POST`: coin reviews, top-trader and wallet-review jobs and their cancel, saved wallets, kept apart from the owner's in `settings/bookmarks_guest.json`; `radar.handle(guest=True)` enforces the same sets; the Monitor, the RPC keys and everything else under `/api/radar/` stay owner-only), every other POST is refused, `/api/trading` is served in full (the owner wants guests to see the wallet and its transactions), and the page gets `window.GUEST = true` to hide other tabs and write controls (the Lab, Trading, Coins Review and Wallets Review tabs stay; a guest's job requests spend the owner's RPC keys). POSTs must be same-site (`same_site()`: Sec-Fetch-Site, else Origin; our pages send no referrer, so a form posts with Origin: null).

## Architecture

Pipeline of independent processes that communicate only through files in the data directory (`/opt/pump-graduated/data` on the server):

- **collector.py** (timer, every 20 min) → `pump.db`: `tokens` + 1-minute `candles` from creation to ~5h after graduation. **first_trades.py** runs right after it and adds each coin's first (creator) trade.
- **holders.py** (always on) → `holders.db`: holder/top-10/creator/sniper/bundler snapshots during each coin's first hour. pump.fun only exposes *current* holders, so these must be recorded live. They're kept in a separate DB so the collector's long writes to `pump.db` never block them.
- **analyze.py** (timer every 6h, and via `rules.path` whenever `settings/rules.json` changes) → `report.json`, `history.json`, and `backtest_*` tables in `pump.db`. Features include `avg_trade_usd_total`, `mins_since_high` and `hour_utc` (added 19 Oct 2026; `hour_utc` is usable in rules but skipped by the search, `SEARCH_SKIP`, since a single cut on a cyclic hour is not a meaningful rule). Eight more features (added 21 Oct 2026, `analyze.shape_features`, from the 1-minute bars only: `grad_high_vs_price`, `dip_depth`, `mins_below_high`, `lower_high_minutes`, `range_5m`, `red_minutes_5m`, `vol_trend_5m`, `mins_since_creation`; the last is skipped by the search). The search also tries every feature as it was 5 and 10 minutes before the entry (`AT_BACK`, never before minute 5; saved as conditions with `at`, as Strategy B20 has them): each of the best `TOP_SINGLES` entry-minute conditions is paired with every earlier-minute condition, and an earlier-minute condition can be the third of a best pair (about 79M rule sets a run instead of 24M; the run takes about 5 minutes and now touches the analyze unit's 320M limit, with about 44M of swap; the combinations are int arrays and the kept masks are bit-packed to save memory). Its rule search (one to three conditions at entry minutes 5–30, thresholds at the 10–90% quantiles, every exit) ranks rule sets on the earliest part of the train coins (`RANK_SHARE` of the earlier 70%), keeps only those that also hold on the rest of the train coins without their 3 best trades and on most days (`MIN_CHECK_TRADES`, `MIN_DAY_SHARE`), picks the best of those, and judges that one pick on the later 30% (verdict `pass` needs `PASS_TEST_TRADES`, a positive bootstrap low end and a positive result without the 3 best). `watch.py` paper-trades the newest search run's pick only when that run's verdict is `pass` (an older pass is not kept: with millions of rule sets an occasional lucky pass is expected); otherwise there is no automatic strategy. Features missing for more than 2% of the ranking coins at an entry minute are left out of the search at that minute. The analyze unit runs numpy single-threaded to stay within the shared host's memory limit. Fee, slippage, stake, and price-impact assumptions are module constants at the top.
- **watch.py** (always on) → `watch.db`, `watch.json`, `watch_tokens/<mint>.json`. It paper-trades the automatic rule, the user's enabled rules, and `rules.WATCH_EXTRA` on new graduates. It sends no Telegram messages: paper trades are silent.
- **trader.py** (always on) → `trades.db`, `trading_state.json`. It acts on fresh live buy signals from watch, swaps through Jupiter, and exits on TP/SL/time-stop measured against Jupiter sell quotes. Its mode comes from `settings/trading.json`: `off` / `dry` / `live`. Live mode signs with `settings/wallet.json`.
- **server.py + index.html**: stdlib HTTP server. It serves the JSON files above and saves rules, Telegram, and trading settings into `data/settings/`. Switching trading to live requires typing `LIVE`.

Key invariants:
- **Backtest/live parity**: `watch.py` measures entry conditions with `analyze.features(...)`, the same function the backtest uses. Any feature change in `analyze.py` changes live behavior, and new features must also be added to `rules.FEATURES` (with a label and a unit kind) so they can be validated and used in rules.
- **Pages** (`index.html`): Record live, Strategy history, Lab (which also edits the rules), Trading and Settings. Settings is laid out like Rug Radar's Settings page: Account (change the password), the Solana RPC the trader uses, the Solana RPC keys of the Coins/Wallets/Monitor pages, Trading wallets, and Telegram alerts (real trades only: `trader.py` messages `tell()` only for live-mode buys and sales and for live-position problems; a dry run or a paper trade sends nothing). `server.py` serves `/api/password`, `/api/rpc` and `/api/rpc/test` (it only ever reveals an RPC address's host, which can hold a key); `/api/account` and `/api/sessions/others` remain but no page uses them. Trading wallets: a private key is pasted on the page (base58 or a list of 64 numbers; only accepted over HTTPS: `server.secure()` reads nginx's `X-Forwarded-Proto`, and the page's form is disabled on plain HTTP; the site is at https://pumpgrad.0xportal.app) and `wallets.py` (pure Python, checks the key and works out its address) saves it as `settings/wallets/<address>.json` (mode 600) with labels in `settings/wallets.json`; the active one is copied to `settings/wallet.json`, which is what `trader.py` loads, and it reloads that file when it changes and no live position is held. Each live trade records its `wallet`. Deleting a wallet (`/api/wallets/remove`, any wallet, refused while positions are open with it; deleting the one in use also deletes wallet.json and sets trading mode off) queues `settings/wallet_purge/<address>`, and `trader.purge_wallets` then deletes all its trades (today's result kept in meta `purged:<day>` for the daily loss limit); `trader.wallet_still_ok()` stops a buy whose key was deleted or switched before it is signed. `/api/wallets` (GET/POST), `/api/wallets/active` and `/api/wallets/remove` never return a key and refuse to change the wallet in use while live positions are open. The old Strategy report and Telegram pages were removed; `report.json` is still written by `analyze.py` because `watch.py` reads it.

It also saves the creator's launch buy and marks the coin `candles_done`, so the backtest grows with the live record even while the collector is paused. `watch.db`'s `tokens.archived` tracks it (1 saved, -1 had no bars). - **Crossing** (`crossing.py`, its own service `pump-graduated-crossing.service`, tab `#crossing`, owner only: `/api/crossing` is not in `GUEST_GET`): a monitor and forward test, it buys nothing. It follows every classic graduate from `watch.db` for its first 14 minutes, reads its 1-minute candles (the forming minute too) every 15 s when the coin is in the dip phase and every 30 s before, and flags the first moment the price tops the graduation price again (`analyze.cross_at` / `crossing_minute`; `analyze.py` and `crossing.py` share it, so they cannot drift). **The rules (rewritten 21 Oct 2026; `analyze.cross_base` / `cross_setup` / `cross_at`, one set of functions for `analyze.py` and `crossing.py`):** each coin's own level is the HIGH of its graduation minute (`c.ref` in `crossing.py`, from `high[0]`; the fixed standard graduation price, $43.7K, is still `Monitor.p0` but only feeds `W.arrays`' stake and `ret_since_grad`; an event carries `ref` (mcap) and one recorded before 20 Oct has none and keeps the old level). 1. The graduation minute (minute 0) closes between $35K and $50K (`CROSS_START_MCAP`, `CROSS_PRE_MCAP`). 2. The highs of minutes 1 and 2 are not above the level. 3. Floor: no minute before the crossing has a low under $15K (`CROSS_FLOOR_MCAP`; minute 0 included, the crossing minute itself not). 4. Ceiling: no minute from 1 to the one before the crossing CLOSED above the level (a wick above it is fine from minute 3 on; until 22 Oct 2026 this looked at highs, which kept out Ginger, whose minute-6 high was 1.3% above the level before it crossed; rule 2 still tests the highs of minutes 1 and 2). 5. Minute m-1 closed below the level and minute m closes at or above it, m from 3 to 12 (`CROSS_FIRST`, `CROSS_LAST`). The earlier dip rules (2 closes below 0.97x the level, 2 minutes with a high no higher than minute 1's) and the $50K close ceiling were dropped on 21 Oct 2026. Backtest of the saved candles (6,844 coins, +100% / -40% / 15 min, bought at the crossing close): with the close-based ceiling 152 crossings, mean -14.9% a trade (earlier 70% -19.3%, newest 30% -8.6%); with the high-based ceiling it was 111 crossings, -17.2% (earlier -28.6%, newest -4.7%); a 2% or 5% tolerance on the highs gave 123 (-16.9%) and 130 (-19.3%); no exit in the grid and none of 175 filters turned it positive (earlier rule sets: fixed level 443 crossings -12.7%; level = minute-0 high with the dip rules 284 crossings -12.7%). 12 of the 44 events recorded on 21 Oct pass the new rules (checked against the pump.fun candles; none deleted yet). Armed (`crossing.py`) = rules 1 to 4 hold so far and the last close is below the level; `out_reason` retires a coin whose low went under the floor, whose minute-1 or minute-2 high topped the level, or that closed above the level before crossing it. **Pattern strategy (22 Oct 2026), also in the Lab as Strategy G** (`rules.WATCH_EXTRA`: entry 6 to 13, condition `pattern_cross_now` = 1, +35% / -50% / 10 min, paper only; `pattern_cross_now` is `analyze.pattern_cross_now`: the coin's first crossing was the minute before the entry minute and `cross_pattern` holds; skipped by the rule search):  a confirmed crossing gets `flags.pattern` (`analyze.cross_pattern`: a crossing from minute 5 on whose minute 0 closed at 72%-90% of its own high, and each of minutes 1-4 closed at most 93% of the level with a high not above it, a body of at most 25% of it and a low not under $25K; found on four charted coins that kept rising, 36 of 152 crossings) and every confirmed event a second paper outcome `outcome2` with `analyze.PATTERN_EXIT` = +35% / -50% / 10 min (the Crossing page's Forward test shows the pattern events' `outcome2` as "Pattern strategy", and `stats.pattern` / `pattern_events` / `pattern_old_exit`; the event cards carry a `pattern` tag and the Telegram confirmed text says PATTERN). Backtest on the 36 coins: +9.1% a trade, 75% won (earlier 70% +3.8%, newest 30% +13.9%, without the best 3 +7.1%, bootstrap -2.3% to +20.1%); at +30% the 1-3 s delay replay gave +8% to +13.5%; +25% to +40% was a plateau; the all-crossings exit gave +1.2% on the same coins; every filter tried on top found nothing. All chosen on the same coins, so only the forward test confirms it. Each watched coin also carries `rows` (`timeline()`), a live status table (time, minute, what happened) that the Watching now panel shows per coin. For an entry before minute 5 `analyze.features` uses the minutes so far scaled to 5. At the flag it reads the trades (`/trades/<chain>/<mint>`, newest first) 60 s before and, 60 s later, 60 s after the crossing (sell share, buyers; "sellers gone" = sellers <= 15% of the dollars and >= 8 buyers); when the crossing minute closes it confirms or marks the event "fell back" (a failed coin can cross again in a later minute), computes `analyze.features` at the entry minute (flags: group = 0.1-10 min from creation to graduation, quiet = at most 857 trades in the last 5 minutes), and once 16 minutes have passed records what a buy at that close would have done (+100% / -40% / 15 min, `analyze.simulate`). - **Pattern Discover** (`patterns.py`, tab `#patterns`, owner only; added 22 Oct 2026): the pattern-discovery skill (`.claude/skills/pattern-discovery`) as a program. `pump-graduated-patterns.timer` runs `pump-graduated-patterns.service` (oneshot, `MemoryMax=320M`) 10 minutes after boot and then every 2 hours; `pump-graduated-patterns.path` runs it when the page's Run now writes `data/jobs/patterns_run.json`. - **Rule format** is defined and validated in `rules.py`: `entry`, optional `entry_to` (added 22 Oct 2026: a range of entry minutes, up to 20 apart; the rule buys at the FIRST minute from `entry` to `entry_to` at which every condition holds, one buy a token; `analyze.entry_view` merges the minutes per coin for the backtest and strategy pages; `watch.py` looks at the rule again each time a new minute inside the range has closed (`_range_eval`, `entry_minutes`, `due`), stores the minute it bought at as the decision's `entry` and as `entry` in the decision's rule snapshot (`snapshot()`, with `entry_from` / `entry_to`), and the live record has an `entry` column per row), `conditions[{feature, op, value, at?}]`, `tp`, `sl`, `hold`, `enabled`, `live`, and optional `be` and `be_stop` (breakeven trigger: once the price has been `be` above the entry, e.g. 0.5 = +50%, the stop moves up to the entry price plus `be_stop`, e.g. 0.1 = +10%, default the entry price; `analyze.simulate(be=)` from the next minute, `trader.py` by the position's `peak_value`, exit reason "breakeven stop"; any rule can use them, set in the Lab's rule editor; B20-direct has 0.5 / 0.1 since 20 Oct 2026, which changes its Lab record start because `be` is part of a rule's core). The server, analyze, and watch all go through it. A condition with `at` (a minute before `entry`) is measured at that minute (`analyze.matches(f, conds, at)` with `features_at`, `watch.check(s, f, at)`); readings and failure counts are keyed by `rules.cond_key` (`feature@minute`). Strategy B20 uses it (Strategy B at minute 15, then a steady price at 20). A strategy's Lab live record (`watch.write_strategy_live`) leaves out tokens whose entry minute ended before that version of the strategy was first seen (`before_rule`): those are catch-up decisions, not live signals.
- **Schema evolution**: DBs grow in place on the server. Code adds columns through migrations (e.g. `analyze.migrate`), and older `holders.db` rows read missing columns as NaN. `deploy/merge_watch.py` merges server `watch.db` snapshots into the local one, adding new columns and preferring server rows, so the local `data/watch.db` keeps history the server has pruned.
- **trader.py order safety**: each order runs in its own thread. Outcomes are read from the order's own transaction, never from wallet balances. An order stays "sent" until its signature is confirmed or its blockhash expires. Interrupted orders are reconciled on startup. Preserve these properties when editing it.
- **Latency**: a `pricer` thread in `trader.py` values open positions straight from the PumpSwap pool about once a second (`price_pools`, one `getMultipleAccounts` call through `rpc_primary`, which has no public-RPC fallback). It checks the pool's base mint and WSOL pairing, and caps the value at the SOL in the vault. Jupiter, whose free allowance is small, is asked every `CALIBRATE_EVERY` s to calibrate a per-trade fee factor in [0.97, 0.9975], and it prices the trade itself when the pool reading is stale or disagrees (`pool_bad`). The main round runs every 0.15 s and reads signals about every 0.3 s. `watch.py` decides each minute `SETTLE` = 1 s after it ends, on up to `DECIDERS` = 4 coins in parallel. Swaps are built from Jupiter's `/swap-instructions` into our own v0 transaction (`compile_tipped`: priority raised to `MIN_PRIORITY_LAMPORTS`, capped by the setting, plus a `SENDER_TIP_LAMPORTS` tip to a Helius Sender tip account), checked unsigned by `inspect_swap` and the 1232-byte limit, signed, and sent to both the RPC and Helius Sender; a local build failure falls back to Jupiter's own `/swap` transaction (`build_swap_plain`), a Jupiter or network error does not. `wait_landed` polls every 0.3 s for 8 s (block height only every 2.5 s). `rpc()` asks the free public RPC when the chosen one cannot be reached (transport errors only; for 30 s afterwards the public one goes first), never on an RPC `error` answer. Also: a Jupiter swap transaction is checked before signing (`inspect_swap`: wallet pays, only `SWAP_PROGRAMS` at the top level, System transfers within the order; add a program to the list if a legitimate route is refused), a live buy needs a quote that echoes the order and a price impact within the `max_buy_impact_pct` setting (Limits and settings on the Trading tab, default 7%, 1-20%; the backtests skip a coin above 5%, `analyze.MAX_IMPACT`), a buy is never written off as failed before the wallet is checked for its tokens (`adopt_held`), rows left by a dead order thread are swept each round, one position's error cannot stop the others' stops, and chosen strategies that are missing from `watch.json` mean nothing is traded.

## Deployment

`deploy/deploy.sh` copies `app/*` to `root@45.76.106.71:/opt/pump-graduated/` and the systemd units to `/etc/systemd/system/`, then restarts the services (they run as the `pumpgrad` user, port 8090). `HOST=root@<ip>` overrides the target for both `deploy.sh` and `pull_db.sh`. 108.61.215.144 is a shared box (it also runs nginx, mail and MariaDB), so it has per-host drop-ins in `/etc/systemd/system/pump-graduated-*.service.d/limits.conf`. These set lower `MemoryMax` values (225M for most, 320M for the analyze/rules/draft backtests since the 19 Oct 2026 features) and run the collector with `--rate 2 --workers 2`. The watch and recorder share pump.fun's limits on that IP, and with 8 workers Cloudflare throttled every candle request from the IP for hours, including the watch's. `deploy.sh` only enables the collect timer, so on a fresh host start it by hand: `systemctl start pump-graduated-collect.timer`. When adding a new script or unit, add it to the `scp` and `systemctl enable` lists in `deploy.sh`. On the server, `solders` lives in `/opt/pump-graduated/lib` (via `PYTHONPATH` in the trader unit). Each unit sets its own `MemoryMax` (100–450M), so keep memory use bounded.

`data/`, `settings/`, `*.db`, and wallet/seed files are gitignored and must never be committed.
