# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A pump.fun "graduated memecoin" system: it records tokens that graduated from the bonding curve to PumpSwap, backtests a "buy N minutes after graduation" strategy, paper-trades the strategies live, and can turn live signals into real swaps. Plain Python 3 scripts (stdlib + `numpy`; `solders` only for live trading) plus a single-page web app. There is no build step, test suite, linter config, or dependency manifest.

## Running locally

Every script lives flat in `app/` and imports its siblings by module name (`import analyze as A`, `import rules`, `import pumpapi as C`, `import notify`), so run them as `python3 app/<script>.py` from the repo root. Most default to `data/` relative to the cwd; `server.py` defaults to `app/data`, so pass `--data data`.

```sh
deploy/pull_db.sh                                   # snapshot the VPS databases + reports into data/
python3 app/analyze.py --db data/pump.db --out data/report.json   # full backtest + rule search
python3 app/analyze.py --rules-only                 # backtest only the saved rules (settings/rules.json)
python3 app/analyze.py --history-only               # rebuild history.json from saved runs
python3 app/server.py --port 8090 --data data       # web app
python3 app/watch.py --data data                    # live paper trading (runs forever)
python3 app/trader.py --data data                   # signal -> swap executor (runs forever)
```

The web app requires a login: `data/settings/login.json` holds `{"salt", "hash"}` (PBKDF2-SHA256), checked in `server.py:password_ok`. A view-only guest password lives in `data/settings/guest.json` (same format): a guest session (`role` "guest", tied to that file's hash, so replacing it signs guests out) may only GET `GUEST_GET` and `/api/strategy/*` (the Lab and Trading pages) and use the Coins Review and Wallets Review pages in full (`radar.GUEST_GET` / `radar.GUEST_POST`: coin reviews, top-trader and wallet-review jobs and their cancel, saved wallets, kept apart from the owner's in `settings/bookmarks_guest.json`; `radar.handle(guest=True)` enforces the same sets; the Monitor, the RPC keys and everything else under `/api/radar/` stay owner-only), every other POST is refused, `/api/trading` is served in full (the owner wants guests to see the wallet and its transactions), and the page gets `window.GUEST = true` to hide other tabs and write controls (the Lab, Trading, Coins Review and Wallets Review tabs stay; a guest's job requests spend the owner's RPC keys). POSTs must be same-site (`same_site()`: Sec-Fetch-Site, else Origin; our pages send no referrer, so a form posts with Origin: null).

## Architecture

Pipeline of independent processes that communicate only through files in the data directory (`/opt/pump-graduated/data` on the server):

- **Archive of bars** (`watch.py`'s `archive_loop`, below) → `pump.db`: `tokens` + 1-minute `candles` from creation to 2 hours after graduation (`analyze.T` = 121 and `rules.LIMITS` since 25 Oct 2026; coins saved before that hold ~5 hours, and `analyze` reads only the first 121 minutes of each). The collector (`collector.py`, the 20-minute timer and `first_trades.py` after it) was removed on 25 Oct 2026: pump.fun throttled it and the archive loop does the same job; its shared helpers (throttled API GET, `SCHEMA`, `is_classic`) are in `pumpapi.py`, and `first_trades.py` (`fetch`, `SCHEMA`) is still used by `watch.py`. `/api/tokens` and `/api/tokens.csv` serve `latest.json` / `latest.csv`, which only the collector wrote (last written 18 Oct 2026).
- **holders.py** (always on) → `holders.db`: holder/top-10/creator/sniper/bundler snapshots during each coin's first hour. pump.fun only exposes *current* holders, so these must be recorded live. They're kept in a separate DB so the collector's long writes to `pump.db` never block them.
- **analyze.py** (timer once a day at 01:00 UTC, and via `rules.path` whenever `settings/rules.json` changes) → `report.json`, `history.json`, and `backtest_*` tables in `pump.db`. Features include `avg_trade_usd_total`, `mins_since_high` and `hour_utc` (added 19 Oct 2026; `hour_utc` is usable in rules but skipped by the search, `SEARCH_SKIP`, since a single cut on a cyclic hour is not a meaningful rule). Eight more features (added 21 Oct 2026, `analyze.shape_features`, from the 1-minute bars only: `grad_high_vs_price`, `dip_depth`, `mins_below_high`, `lower_high_minutes`, `range_5m`, `red_minutes_5m`, `vol_trend_5m`, `mins_since_creation`; the last is skipped by the search). The search also tries every feature as it was 5 and 10 minutes before the entry (`AT_BACK`, never before minute 5; saved as conditions with `at`, as Strategy F++ has them): each of the best `TOP_SINGLES` entry-minute conditions is paired with every earlier-minute condition, and an earlier-minute condition can be the third of a best pair (about 79M rule sets a run instead of 24M; the run takes about 5 minutes and now touches the analyze unit's 320M limit, with about 44M of swap; the combinations are int arrays and the kept masks are bit-packed to save memory). Its rule search (one to three conditions at entry minutes 5–30, thresholds at the 10–90% quantiles, every exit) ranks rule sets on the earliest part of the train coins (`RANK_SHARE` of the earlier 70%), keeps only those that also hold on the rest of the train coins without their 3 best trades and on most days (`MIN_CHECK_TRADES`, `MIN_DAY_SHARE`), picks the best of those, and judges that one pick on the later 30% (verdict `pass` needs `PASS_TEST_TRADES`, a positive bootstrap low end and a positive result without the 3 best). `watch.py` paper-trades the newest search run's pick only when that run's verdict is `pass` (an older pass is not kept: with millions of rule sets an occasional lucky pass is expected); otherwise there is no automatic strategy. Features missing for more than 2% of the ranking coins at an entry minute are left out of the search at that minute. The analyze unit runs numpy single-threaded to stay within the shared host's memory limit. Fee, slippage, stake, and price-impact assumptions are module constants at the top.
- **watch.py** (always on) → `watch.db`, `watch.json` (only what the trader and the Trading tab need: the strategies, `tradable`, `sol_usd`; the per-token rows, `watch_tokens/<mint>.json` and the daily `reports/*.csv` of the removed Record live page are gone) and the Lab's `strategies/<id>.live.json` (every 30 minutes, `LAB_EVERY`). It paper-trades the automatic rule, the user's enabled rules, and `rules.WATCH_EXTRA` on new graduates. It sends no Telegram messages: paper trades are silent.
- **trader.py** (always on) → `trades.db`, `trading_state.json`. It acts on fresh live buy signals from watch, swaps through Jupiter, and exits on TP/SL/time-stop measured against Jupiter sell quotes. Its mode comes from `settings/trading.json`: `off` / `dry` / `live`. Live mode signs with `settings/wallet.json`.
- **server.py + index.html**: stdlib HTTP server. It serves the JSON files above and saves rules, Telegram, and trading settings into `data/settings/`. Switching trading to live requires typing `LIVE`.

Key invariants:
- **Backtest/live parity**: `watch.py` measures entry conditions with `analyze.features(...)`, the same function the backtest uses. Any feature change in `analyze.py` changes live behavior, and new features must also be added to `rules.FEATURES` (with a label and a unit kind) so they can be validated and used in rules.
- **Pages** (`index.html`): Recorder, Strategy history, Lab (which also edits the rules), Trading and Settings. Settings is laid out like Rug Radar's Settings page: Account (change the password), the Solana RPC the trader uses, the Solana RPC keys of the Coins/Wallets/Monitor pages, Trading wallets, and Telegram alerts (real trades only: `trader.py` messages `tell()` only for live-mode buys and sales and for live-position problems; a dry run or a paper trade sends nothing). `server.py` serves `/api/password`, `/api/rpc` and `/api/rpc/test` (it only ever reveals an RPC address's host, which can hold a key); `/api/account` and `/api/sessions/others` remain but no page uses them. Trading wallets: a private key is pasted on the page (base58 or a list of 64 numbers; only accepted over HTTPS: `server.secure()` reads nginx's `X-Forwarded-Proto`, and the page's form is disabled on plain HTTP; the site is at https://pumpgrad.0xportal.app) and `wallets.py` (pure Python, checks the key and works out its address) saves it as `settings/wallets/<address>.json` (mode 600) with labels in `settings/wallets.json`; the active one is copied to `settings/wallet.json`, which is what `trader.py` loads, and it reloads that file when it changes and no live position is held. Each live trade records its `wallet`. Deleting a wallet (`/api/wallets/remove`, any wallet, refused while positions are open with it; deleting the one in use also deletes wallet.json and sets trading mode off) queues `settings/wallet_purge/<address>`, and `trader.purge_wallets` then deletes all its trades (today's result kept in meta `purged:<day>` for the daily loss limit); `trader.wallet_still_ok()` stops a buy whose key was deleted or switched before it is signed. `/api/wallets` (GET/POST), `/api/wallets/active` and `/api/wallets/remove` never return a key and refuse to change the wallet in use while live positions are open. The old Strategy report and Telegram pages were removed; `report.json` is still written by `analyze.py` because `watch.py` reads it.
- **Recorder** (`#recorder`, the first page; `recorder.py`, owner only; replaced the Record live page and its code on 25 Oct 2026, laid out like Rug Radar's Recorder page `~/sol-meme/public/recorder.html`): `/api/recorder` (coins being recorded now: tokens `new` or `active` within 120 minutes of graduation, with decisions, buys and the market caps measured at the entry minutes as a sparkline; today's counts, **late decisions today** (made over 3 minutes after their minute: the number that showed the WIN stall of 25 Oct 2026), SOL price; the recorded days), `/api/recorder/coins?day=` (every coin of a UTC day: launch kind, detection delay, whether its bars are saved, first market cap, decisions, buys, result in SOL) and `/api/recorder/coin?mint=` (the coin's 1-minute bars from `pump.db` as market cap = price x 1e9, with a chart marking each buy, and every strategy's decision, exit and result). It reads `watch.db` and `pump.db` read-only (queries start from the day's tokens through `tokens_grad` and use `decisions_decided`, so no page scans a table); a finished day's list is cached for 10 minutes. The page also holds the Stored data panel (`/api/storage`). Old `#tokens` links open it. Not ported from Rug Radar: its strategy-backtest form (the Lab does that) and its 1-2 second samples (ours are 1-minute bars).
- **Archive**: `watch.py`'s `archive_loop` thread saves each graduate's complete 1-minute bars into `pump.db` (the tables `analyze.py` reads), one request every 3 seconds, once the coin is 124 minutes old. It also saves the creator's launch buy and marks the coin `candles_done`, so the backtest grows with the live record even while the collector is paused. `watch.db`'s `tokens.archived` tracks it (1 saved, -1 had no bars). A coin the collector already holds complete is skipped.
- **Lab** (`#lab` in `index.html`, laid out like Rug Radar's Minute lab; it replaces the old Rules tab, and `#rules` opens it): only the built-in rules (`rules.WATCH_EXTRA`, since 25 Oct 2026: B20-direct, E, H+, I, F+ and F++, all paper only; Strategies A, B, B20, B+, C, C+, C-steady, D, F, G and H were deleted from the Lab by the owner and their code removed on 25 Oct 2026; the trader buys only strategies switched ON on the Trading tab) side by side; the Trading tab's strategy list shows the same set. Saved or starter rules in `settings/rules.json` still exist and run in `watch.py`/`analyze.py`, but no page lists them, and there is no New rule button. Per rule: Edit, ON/OFF, Delete, Details and Backtest. Saving an edited built-in stores an override under its id in `settings/rules.json`. Delete on a built-in calls `POST /api/rules/builtin` {id, removed}: the id goes into `settings/rules_removed.json` (`rules.removed`/`set_removed`; `rules.with_extras(saved, removed)` leaves it out in analyze, watch and the server's built-in list), any override is dropped, and the Lab lists it under the table with a Restore button. The server refuses while the strategy is switched ON on the Trading tab or holds a live position (the trader trades nothing when none of its chosen strategies is recorded), and `POST /api/trading` drops removed ids; both run under `_save_lock`. `New rule` and Edit open a dialog (`openRuleEditor`) and save through `POST /api/rules`, which fires `rules.path` so `analyze.py --rules-only` and `watch.py` (reloads every 60s) redo that rule's backtest and live record. `Backtest without saving` posts the rule to `POST /api/lab/draft` (`settings/draft.json`); `pump-graduated-draft.path` runs `analyze.py --draft`, which writes `data/draft-result.json` that `GET /api/lab/draft` returns (the web service cannot run the heavy work itself). Each rule's backtest is `data/strategies/<id>.json` (`write_strategy_pages`, stale files pruned) and its live paper record `<id>.live.json` (`watch.write_strategy_live`); `server.py` serves `/api/strategies`, `/api/strategy/<id>` and `/api/strategy/<id>/live`. A rule with an open `live` position in `trading_state.json` is highlighted. The Lab's top line counts down to the next full backtest from `GET /api/backtest/schedule` (`server.backtest_schedule`: `systemctl show` on the analyze service, the next 01:00 UTC (the timer's `OnCalendar`), the last run's end from the service, falling back to `report.json`'s age) and says when a backtest is running now. Old `#strategy/<id>` links open that rule in the Lab.
- **Trading tab** (`renderTrading` in `index.html`, laid out like Rug Radar's Trading page): reads `trading_state.json` every 3 seconds and saves through `/api/trading`. Each strategy has an ON/OFF switch that saves its list at once. **Time-of-day filter** (23 Oct 2026): Limits and settings has a row of 24 UTC-hour buttons (`trade_hours` in `settings/trading.json`, a sorted list of hours 0-23; none chosen = every hour; `trader.clean_cfg` / `trader.hours_open`): `Trader.consider` lets an automatic signal go (nothing recorded) when the current UTC hour is not chosen. A sale is asked through `/api/trading/sell` with two clicks. `trader.py` also writes each trade's `tp`, `sl` and `hold_until` to the state file for the open-positions table.
- **Crossing (removed 24 Oct 2026)**: the Crossing page, its monitor (`crossing.py`, `pump-graduated-crossing`), the Crossing trader (`pump-graduated-crossing-trader`, buys by hand, its own wallet, `/api/ct/*`, `data/crossing/`) and the Telegram `events` settings were deleted, on the server too (its data, wallet key file and 4 recorded trades included). **Kept, because Pattern Discover (its `cross` family) uses them:** the crossing rules in `analyze.py` (`cross_base` / `cross_setup` / `cross_at` / `crossing_minute` / `first_crossings` / `cross_pattern` / `pattern_cross_now`, `CROSS_*`, `PATTERN_EXIT`): a coin's level is the HIGH of its graduation minute; minute 0 closes $35K-$50K; the highs of minutes 1-2 are not above the level; no low under $15K before the crossing; no close above the level before it; minute m-1 closed below the level and minute m (3 to 12) closes at or above it.
- **Dip watch** (`dipwatch.py`, its own service `pump-graduated-dipwatch.service`, tab `#dipwatch`, owner only: `/api/dipwatch` is not in `GUEST_GET`; added 24 Oct 2026): a recorder and forward test for Rug Radar's (`~/sol-meme`, `src/trade/paperlab.js`) "Danger dip + whale buy (tight exit, big pool)": a Danger launch with an X link and a website, created and graduated in one block, 1 to 5 minutes after graduation, market cap $80K+, the price down 30%+ over the last minute, a buy of 5+ SOL in the last 30 s, a pool of 110+ SOL; sold at x1.5 / x0.5 / 30 min. Our stored data (1-minute bars) cannot test it: the 5 SOL buy and the pool are not recorded, and the 1-second candles reach back only about 7 days. The service takes the coins from `watch.db` the way the removed Crossing monitor did, keeps only the ones that pass the static tests (classic curve, X link and website, `graduated_ts - created_ts` at most 3 s = one block: both are stored to the second for recent coins), reads each one's 1-minute candles every 10 s from 45 s to 330 s after graduation, and when the price is 20%+ under the last close (or 25%+ under the forming minute's high) at $70K+ it reads the trades (`dipwatch.fetch_trades`, newest first, up to 8 pages: the exact price 60 s ago, the biggest buy of the last 30 s in SOL), the pool's SOL (the pool account's SOL vault, `solana.call` through the RPC key pool, vault addresses cached) and the latest `holders.db` snapshot (bundlers / dev 50%+ as a rough Danger proxy), and stores a reading with every condition as its own flag (`c_age`, `c_mcap`, `c_drop`, `c_whale`, `c_pool`). The first reading with the dip conditions is a `dip` entry, the first with all of them a `full` entry (entry price = the reading's price, 1.5 s delay not modelled); 31 minutes later each gets its result from the 1-minute candles (the entry minute is skipped, stop first, stop slippage, fees, impact as in `analyze.net_return`). `data/dipwatch.json` (the page) and `data/dipwatch.db` (`readings`, `entries`). **Paper trade** (24 Oct 2026): every entry is a paper trade of `analyze.STAKE_SOL` (0.1 SOL), bought at the open of the first 1-second candle after `entry_ts` (the reading + 1.5 s) and followed second by second on pump.fun's 1-second candles (`seconds()`, `paper()`: a cursor, up to 8 pages of 300 s per poll, polled every 10 s while open) until a second touches x1.5 (target, fills at x1.5) or x0.5 (the stop first inside a second, `min(open, stop, close)` x (1 - `SL_SLIP`)) or 30 minutes pass (last close); `net_of()` applies fees and price impact as `analyze.net_return`; `outcome` carries `pnl_sol`, `second_level`, `closed_ts`, and `paper` (cursor, p0, last, peak, low) shows an open trade. A coin whose 1-second candles never come (they exist for about 7 days) falls back to the 1-minute result (`paper_failed`). The page's Paper trades panel shows the P&L of the full signal and of the dip entries, the open trades, and each closed entry's SOL result. On a re-run at second level the first TACITY entry changed from target to stop (the price one second after the reading was 23% higher). Backtest of the static tests on the saved bars (219 coins, no whale / pool condition): -18.6% a trade; with a 1-second proxy for the buy (93 coins from the last week) the groups with and without a big up-second were +5.1% and -22.8%. Nothing is bought; if the recorded data supports it, a paper strategy and later a live one can reuse the detector.
- **Dip watch live trading** (26 Oct 2026; `diprule.py`, `trader.dip_signals`): the Dip watch's two kinds of entry are two strategies of the Trading tab, `dip-watch-full` ("Dip watch full signal", all five conditions) and `dip-watch-dip` ("Dip watch dip entry", the broader one), each switched ON or OFF there; both exit at +50% / -50% / 30 minutes (`diprule.TP/SL/HOLD`, which `dipwatch.py` also uses for its paper trades, so the two cannot drift apart). `trader.py` reads fresh rows of `dipwatch.db` `entries` (`read_ts` within `diprule.SIGNAL_FOR` = 20 s; a row is written at the reading, its later updates are the paper trade's progress and do not change `read_ts`) about 3 times a second next to the watch's decisions, and sends them through the same `Trader.consider` as any strategy: nothing is added, so the stake, `max_open`, the daily loss limit, the UTC hours, one live position per coin (a coin that triggers both kinds is bought by whichever is processed first), Telegram, the sale buttons and the latency columns all apply. `signal_ts` and `entry_ts` of such a trade are the price reading's time (the paper trade buys 1.5 s later), so `lat_seen_ms` and 'confirmed X s after the signal' count from the reading and the time stop counts from it. The strategies are added to `trade_strategies`'s list in `trader.py` (not to watch.json) with a `note`, which the Trading page shows instead of 'Buys at minute N' and which lets them through its Lab-rule filter. Their backtest column is empty: the Dip watch's own paper record is on its page and is not a backtest.
- **Pattern Discover** (`patterns.py`, tab `#patterns`, owner only; added 22 Oct 2026): the pattern-discovery skill (`.claude/skills/pattern-discovery`) as a program. `pump-graduated-patterns.timer` runs `pump-graduated-patterns.service` (oneshot, `MemoryMax=320M`) 10 minutes after boot and then every 2 hours; `pump-graduated-patterns.path` runs it when the page's Run now writes `data/jobs/patterns_run.json`. A pass: seeds = coins whose minute 0 closed $30K-$50K and that peaked above $90K within 30 minutes (since 22 Oct 2026; the patterns themselves are tested on coins whose minute 0 closed $35K-$50K, `M0_LO` / `M0_HI`), from the earlier 70% of the coins only; candidates (about 270) in two families from the seeds' quantiles (`cross`: the first crossing after a quiet start, `jump`: the first big jump after quiet minutes), three exits each (`EXITS`), plus the hand-found ones (`HAND`: the quiet-then-jump one); each is backtested on every saved coin (the backtest's model) and PROFITABLE when it has at least 25 trades and averages more than 7% a trade overall (`MIN_MEAN`, since 22 Oct 2026), is positive on the earlier 70%, on the newest 30% and without its best 3; candidates trading nearly the same coins (80% overlap) count once. Profitable patterns go on the watch list (`data/settings/patterns.json`, up to 60), are backtested again at every pass on all the data, and are tracked on the coins that graduated after they were found (`forward`: testing under 10 such trades, then confirmed or failing); one whose all-data average turns negative is retired. Removing a pattern on the page adds its id to `settings/patterns_removed.json` (the web service may write settings and jobs only; `/api/patterns` hides removed ids at once and the pass skips them). The page reads `data/patterns.json`. **Add to Lab** (23 Oct 2026): a pattern's detail panel has an Add to Lab button -> `POST /api/patterns/lab` {id} (owner only): the pattern (`name`, `spec`) goes into `settings/lab_patterns.json`, which `rules.load_patterns` (called first by `rules.load`, so every process that loads the saved rules knows it) turns into a flag feature `pattern:<id>` in `rules.FEATURES` (`rules.PATTERNS`), and the rule `patterns.lab_rule` made (entry `Q+2` to 13, the condition `pattern:<id>` = 1, the pattern's exit; id `pattern-<id>`; the pass stores it as `lab_rule` on each pattern) is saved with the other rules, so `analyze.py`/`watch.py` backtest and record it like any saved rule. `analyze.pattern_features` computes the flag from a `patterns.Lean` view (minutes 0-13 of the frame, cached per frame) = `chosen_minutes(spec) == entry-1`; the search skips `pattern:` features. The Lab lists these rules with the built-in ones (`GET /api/rules` appends saved `pattern-*` rules to `builtin`, tagged 'from Pattern Discover'); Delete (`/api/rules/builtin`) removes the rule and its `lab_patterns.json` entry outright (no Restore; add it again from Pattern Discover). The Lab backtest of a pattern matches its Pattern Discover numbers exactly (checked 23 Oct 2026: 59 trades +14.38% and 37 trades +9.74%). About 270 candidates are tried per pass, so some pass by luck: only the forward record is a test. Rules for adding candidates: keep their numbers derived from the earlier-70% seeds, never tune on the newest 30%. **Daily discovery** (`patterns.daily_discovery`, 22 Oct 2026): inside the same pass, every 8 hours (`DAILY_S`, gated by `daily.ts` in `settings/patterns.json`; the page's Run now forces it), the skill's method runs on all coins of the 24 hours before the newest saved coin: the day's seeds (same seed rule) give the candidates' numbers (`candidates(seeds=, min_seeds=8, hand=False)`), and each candidate is tested only on the coins OUTSIDE the day (`search(D, cands, ~day)`, the usual pass criteria), so the day is never part of the test; the day's own result is shown as in-sample. Profitable ones join the watch list with origin `daily`. The Pattern Discover page shows a Daily discovery panel from `patterns.json`'s `daily`.
- **Strategy H+** (23 Oct 2026, `rules.WATCH_EXTRA`, paper only; Strategy H, the same without the 70% floor, was deleted 25 Oct 2026): a quiet start after graduation (minute 0 closes $30K-$60K at 72%-92% of its high; minutes 1-3 close at most 93% of it with a high not above it, a body of at most 25%, a low of at least $25K, mean volume at most 75% of minute 0's, every 1-minute bar's high-low at most $5K, and the lowest close of minutes 1-3 at 70% of it or more), bought at the close of minute 3 (**entry 4**, the earliest entry in the system, so `LIMITS['entry']` starts at 4), +100% / -50% / 30 min. - **Coins Review, Wallets Review and Monitor** (tabs `#coins`, `#wallets`, `#monitor`; the tabs and pages were named Coins and Wallets until 20 Oct 2026, owner only; ported from Rug Radar `~/sol-meme` on 20 Oct 2026): the browser code is `radar.js` (Monitor, shared helpers) and `radar2.js` (Coins, Wallets), loaded before `index.html`'s own script, so a top-level `const` there must not repeat a name from `index.html` (it would kill the whole page). They use their own pool of Solana RPC keys, shown and edited on the Settings page (the "Solana RPC keys" panel, `rpcKeysPanel` in `radar.js`, laid out like Rug Radar's Settings page; the Monitor page links to it) and saved as `settings/rpc_pool.json` (mode 600; `{mode: failover|roundrobin, endpoints: [{id, label, url, enabled}]}`; a bare Alchemy key or an https address; copied from Rug Radar's `data/settings.json` on 20 Oct 2026). `solana.call` picks a key per request: a 429 or an RPC rate-limit error rests that key (1.5 s doubling to 60 s, with a learned per-second limit), an outage rests it 5-60 s, a refused key (401/403) 10 minutes, and the next key takes over; failover uses the first ready key, round-robin the least loaded. Rest state is per process (web, monitor and jobs each keep their own). The older single `settings/analysis_rpc.json` still works when the pool is empty; with neither, the slow public RPC. The trader's RPC is never shared. `solana.py` also keeps every transaction read in `data/tx_cache/` (pruned to a day / 1 GB) and gets SOL prices from Binance. `walletparse.py` turns a jsonParsed transaction into a wallet row (buy/sell/swap/transfer...). **Monitor**: `monitor.py` (service `pump-graduated-monitor`) reads each wallet's new signatures every 5 s (30 s while the RPC rate-limits), keeps trades as events in `wallet-watch.json` and sends Telegram messages through its own bot (`settings/watch_telegram.json`); the wallets and options are `settings/watch.json`, written by the server; a new or resumed wallet starts from its `added` time. **Coins**: `coins.py` (DexScreener + GeckoTerminal + RugCheck + a Jupiter quote check, scored like Rug Radar's `analyze.js`) runs in the web service; the **Top traders** analysis and the **Wallets** review (`traders.py`, `wallet_review.py`) are heavy, so the web service only writes a request into `data/jobs/` and the worker service `pump-graduated-jobs` (`jobs.py`) runs it, keeping progress and the result in `data/jobs/<key>.json` (cancel = a `.cancel` file); saved wallets are `settings/bookmarks.json`. The web unit runs with `ProtectSystem=strict` and may write only `data/settings` and `data/jobs` (its `ReadWritePaths`; `deploy.sh` creates `data/jobs`): a new file the web service must write needs its folder added there, and a check run with `runuser` alone does not show the sandbox, so test inside it (`nsenter -t <MainPID> -m runuser -u pumpgrad -- env PYTHONPATH=/opt/pump-graduated python3 ...`).
- **Menu** (22 Oct 2026): the page tabs are a fixed left sidebar (`header.top#side`, grouped Overview / Strategies / Research / Account, inline SVG icons, 252px; collapsible to icons, remembered in localStorage `sideCollapsed`; on screens up to 900px an off-canvas drawer opened by `#menuBtn`, hidden with `visibility` while closed; a guest gets only its four pages and `pruneNavGroups` removes empty groups). The tab links are still `nav.tabs a[data-tab]`, which `showTab` marks `.on`. A new page needs its link in that markup, its `tab-*` section and an entry in `showTab`.
- **Look**: `index.html` and the login page in `server.py` use the design tokens, fonts and components of the Rug Radar app (`~/sol-meme/public/common.css`), with light and dark modes. The older token names (`--page`, `--ink-2`, `--series`, …) are kept as aliases because the page's script uses them in inline styles.
- **Rule format** is defined and validated in `rules.py`: `entry`, optional `entry_to` (added 22 Oct 2026: a range of entry minutes, up to 20 apart; the rule buys at the FIRST minute from `entry` to `entry_to` at which every condition holds, one buy a token; `analyze.entry_view` merges the minutes per coin for the backtest and strategy pages; `watch.py` looks at the rule again each time a new minute inside the range has closed (`_range_eval`, `entry_minutes`, `due`), stores the minute it bought at as the decision's `entry` and as `entry` in the decision's rule snapshot (`snapshot()`, with `entry_from` / `entry_to`), and the live record has an `entry` column per row), `conditions[{feature, op, value, at?}]`, `tp`, `sl`, `hold`, `enabled`, `live`, and optional `be` and `be_stop` (breakeven trigger: once the price has been `be` above the entry, e.g. 0.5 = +50%, the stop moves up to the entry price plus `be_stop`, e.g. 0.1 = +10%, default the entry price; `analyze.simulate(be=)` from the next minute, `trader.py` by the position's `peak_value`, exit reason "breakeven stop"; any rule can use them, set in the Lab's rule editor; B20-direct has 0.5 / 0.1 since 20 Oct 2026, which changes its Lab record start because `be` is part of a rule's core). The server, analyze, and watch all go through it. A condition with `at` (a minute before `entry`) is measured at that minute (`analyze.matches(f, conds, at)` with `features_at`, `watch.check(s, f, at)`); readings and failure counts are keyed by `rules.cond_key` (`feature@minute`). Strategy F++ uses it (a price condition measured at minute 5). A strategy's Lab live record (`watch.write_strategy_live`) leaves out tokens whose entry minute ended before that version of the strategy was first seen (`before_rule`): those are catch-up decisions, not live signals.
- **Schema evolution**: DBs grow in place on the server. Code adds columns through migrations (e.g. `analyze.migrate`), and older `holders.db` rows read missing columns as NaN. `deploy/merge_watch.py` merges server `watch.db` snapshots into the local one, adding new columns and preferring server rows, so the local `data/watch.db` keeps history the server has pruned.
- **trader.py order safety**: each order runs in its own thread. Outcomes are read from the order's own transaction, never from wallet balances. An order stays "sent" until its signature is confirmed or its blockhash expires. Interrupted orders are reconciled on startup. Preserve these properties when editing it.
- **Latency**: a `pricer` thread in `trader.py` values open positions straight from the PumpSwap pool about once a second (`price_pools`, one `getMultipleAccounts` call through `rpc_primary`, which has no public-RPC fallback). It checks the pool's base mint and WSOL pairing, and caps the value at the SOL in the vault. Jupiter, whose free allowance is small, is asked every `CALIBRATE_EVERY` s to calibrate a per-trade fee factor in [0.97, 0.9975], and it prices the trade itself when the pool reading is stale or disagrees (`pool_bad`). The main round runs every 0.15 s and reads signals about every 0.3 s. `watch.py` decides each minute `SETTLE` = 1 s after it ends, on up to `DECIDERS` = 4 coins in parallel. Swaps are built from Jupiter's `/swap-instructions` into our own v0 transaction (`compile_tipped`: priority raised to `MIN_PRIORITY_LAMPORTS`, capped by the setting, plus a `SENDER_TIP_LAMPORTS` tip to a Helius Sender tip account), checked unsigned by `inspect_swap` and the 1232-byte limit, signed, and sent to both the RPC and Helius Sender; a local build failure falls back to Jupiter's own `/swap` transaction (`build_swap_plain`), a Jupiter or network error does not. `wait_landed` polls every 0.3 s for 8 s (block height only every 2.5 s). `rpc()` asks the free public RPC when the chosen one cannot be reached (transport errors only; for 30 s afterwards the public one goes first), never on an RPC `error` answer. Also: a Jupiter swap transaction is checked before signing (`inspect_swap`: wallet pays, only `SWAP_PROGRAMS` at the top level, System transfers within the order; add a program to the list if a legitimate route is refused), a live buy needs a quote that echoes the order and a price impact within the `max_buy_impact_pct` setting (Limits and settings on the Trading tab, default 7%, 1-20%; the backtests skip a coin above 5%, `analyze.MAX_IMPACT`), a buy is never written off as failed before the wallet is checked for its tokens (`adopt_held`), rows left by a dead order thread are swept each round, one position's error cannot stop the others' stops, and chosen strategies that are missing from `watch.json` mean nothing is traded.

## Deployment

`deploy/deploy.sh` copies `app/*` to `root@45.76.106.71:/opt/pump-graduated/` and the systemd units to `/etc/systemd/system/`, then restarts the services (they run as the `pumpgrad` user, port 8090). `HOST=root@<ip>` overrides the target for both `deploy.sh` and `pull_db.sh`. 108.61.215.144 is a shared box (it also runs nginx, mail and MariaDB), so it has per-host drop-ins in `/etc/systemd/system/pump-graduated-*.service.d/limits.conf`. These set lower `MemoryMax` values (225M for most, 320M for the analyze/rules/draft backtests since the 19 Oct 2026 features). The watch and recorder share pump.fun's limits on that IP (the removed collector's 8 workers got every candle request from the IP throttled by Cloudflare for hours, including the watch's), so keep new pump.fun traffic low. When adding a new script or unit, add it to the `scp` and `systemctl enable` lists in `deploy.sh`. On the server, `solders` lives in `/opt/pump-graduated/lib` (via `PYTHONPATH` in the trader unit). Each unit sets its own `MemoryMax` (100–450M), so keep memory use bounded.

`data/`, `settings/`, `*.db`, and wallet/seed files are gitignored and must never be committed.
